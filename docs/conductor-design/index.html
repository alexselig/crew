Start here

The idea you drew

Your sketch had one conductor fanning out to three agents, their work converging back through git into tests and a merge.

The real problem

What actually goes wrong

Two agents in one working copy is not a coordination problem. It is a data-loss problem.

Today every Crew session runs in the directory it was spawned in, and that directory is fixed for the session's whole life — cwd is set at spawn and is part of the session's identity key. Point two agents at one repository and they share a working tree, an index, and a HEAD. They will:

  • stage each other's half-finished files into their own commits,
  • trip over each other's .git/index.lock,
  • and check out branches from under one another mid-edit.

So the first job is not orchestration. It is giving each agent somewhere private to stand, and then letting exactly one thing at a time move the shared branch.

Architecture

Lanes and the integration owner

Agents work in parallel. Landing work is single-file. Those are two different rules and conflating them was the first draft's mistake.

An earlier version passed a baton: only the agent holding it could work. That serialises the thing you wanted parallel and leaves agents idle. The design now separates them:

  • Lanes run concurrently. Nothing stops two agents editing at once — that is the point of the feature.
  • Publication is single-flight. One lock. One lane at a time moves the integration branch.

  • Verified / owned by Crew
  • Failure path
  • Provisional / open

Why the integration worktree is detached

Its HEAD deliberately points at a commit, not at the branch. If a worktree has crew/integration checked out, advancing the ref underneath it leaves that worktree's files and index describing the old commit — the same desync that makes writing to your checkout unsafe. Crew checks git worktree list immediately before advancing, and refuses if anyone has the branch out.

The core mechanism

The publication transaction

Everything that can corrupt a repository happens here, so this is the part that is specified to the step.

When a lane has commits and wants to land them, it asks to publish. The lock admits one. Everything below happens inside it.

What review caught

The bug four reviews took to find

The spec was reviewed by Grok 4.7, GPT-6 Sol, GPT-6 Astra and Claude Opus 5.5. The first three converged on the same ten issues. The fourth found this, which none of them saw, and it would have broken the feature on day two.

The draft published by rebasing the lane's commits onto the integration branch. Rebase rewrites commits — same changes, new SHAs. The rewritten commits land on the integration branch, but the lane's own branch still points at the originals.

The part that actually bites

Git can usually cope with this: a second rebase drops commits whose patch-id already exists upstream. But a patch-id is computed over the diff including its context lines. The moment a teammate edits anywhere near your code, the context changes, the patch-ids stop matching, and git faithfully replays your already-landed commits on top of themselves — conflicting your work against itself, on every subsequent publication.

So the failure does not appear in the first demo. It appears once two lanes have both landed something, which is the exact scenario the feature exists for.

The fix

Merge, and the Sync you now need

Publish by merge instead. Nothing is rewritten, so the lane's commits become genuine ancestors of the integration branch and ahead falls back to zero by itself. No bookkeeping, no reset, no special case.

One promise had to be downgraded — honestly

The draft promised "agents never touch git." Sync means a lane receives merges, so that promise is no longer literally true and pretending otherwise would hide a real risk. The replacement is narrower and actually enforceable: only Crew moves the integration ref. If an agent runs git anyway, the compare-and-swap at step 10 catches it and stops.

Coordination

How agents talk

You asked for agents that coordinate so check-ins don't conflict. They do — but through Crew, never directly.

Every message is a fact Crew verified, not an agent's claim. When a lane lands work, Crew posts a bulletin to the others naming the real commit and the real paths, because Crew performed the merge and read the result.

Honesty

What this does and does not promise

The first draft claimed conflicts were impossible. They are not. This table replaced that claim.

ClaimStatusWhy
Agents cannot corrupt each other's working tree Guaranteed Separate worktrees, separate indexes. Structural.
Only one thing advances the integration branch Guaranteed Single-flight lock plus a ref compare-and-swap.
Your own checkout is never written to Guaranteed It is never a merge target. You merge when you choose.
Textual conflicts are caught before landing Guaranteed The merge happens in Crew's worktree, or it fails.
Two agents writing incompatible designs are stopped No Git merges text. Only your test command can catch semantics — and only if it covers it.
An agent running git itself is prevented No — detected Nothing can stop a shell. The CAS refuses and surfaces it rather than silently proceeding.
Bulletins arrive promptly Eventual Held until the target session is idle. A busy agent hears late.

Settled

Three decisions you made

1 — Review gates publication ✓

A candidate is frozen at an exact SHA, handed to a reviewer, and the merge is gated on a verdict for that SHA. A "needs changes" verdict that cannot stop anything is a comment, not a review.

The consequence worth knowing: review never holds the publication lock. A review is an LLM turn, and the lock is single-flight across the run — holding it across a review would serialise every lane behind one reviewer's thinking time, which is the opposite of why lanes exist. So the candidate is frozen, review runs lock-free, and only an approved lane contends for the lock, where the runtime rechecks that the tip is still the SHA that was approved.

2 — Phase 1 first ✓

The git safety layer with a manual Publish button. Nothing automated, but nothing can eat your repository either — and it is fully testable against a temp repo with no agent in the loop. All four reviewers recommended this, with the 1b transport spike running alongside rather than after.

3 — Cross-model review is the default ✓

Section 7 is in the spec: a lane's identity is (presetId, model), and a reviewer runs on a different vendor's model than the author. This document is the evidence — three reviewers agreed with each other, and the fourth, from a different vendor, found the bug that broke the publication lifecycle.

Next step: the implementation plan for Phase 1. No Conductor code has been written yet, by design.
